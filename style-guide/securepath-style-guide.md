## Purpose

This style guide defines the writing standards for all user-facing documentation for the SecurePath Platform. Apply these rules consistently across all documents — whether writing from scratch or processing developer drafts.

---

## 1. Terminology

Consistent terminology is the single most important quality factor in technical documentation. Use the approved terms below in every document.

### Product terminology

| Use this | Never use this |
|---|---|
| passkey | FIDO2 credential, WebAuthn credential, platform authenticator, resident key, FIDO2 passkey |
| SecurePath | the platform, the system, the application, the product, the tool |
| two-factor authentication (2FA) | MFA, multi-factor authentication, second factor, two-step verification |
| authenticator app | TOTP app, OTP app, time-based app — you may name specific apps (Google Authenticator, Authy) only in illustrative lists |
| backup code | recovery code, one-time code, emergency code |
| sign in | log in, login, log-in |
| sign out | log out, logout, log-off |
| set up (verb) | setup (noun only — "the setup is complete") |
| two-factor authentication is enabled | 2FA is turned on, 2FA is activated, 2FA is switched on |

### First use rule

On first use in a document, write the full term followed by the abbreviation in parentheses: **two-factor authentication (2FA)**. Use the abbreviation alone on all subsequent uses in the same document.

## 2. Voice and person

### Second person
Address the reader directly. Use **you** throughout — not "the user", "the administrator", "users", or "one".

| Correct | Incorrect |
|---|---|
| You can set up a passkey from the Security settings. | The user can set up a passkey from the Security settings. |
| If you lose access to your device, you can use a backup code. | If a user loses access to their device, they can use a backup code. |

### Active voice
Construct sentences so the subject performs the action.

| Correct | Incorrect |
|---|---|
| SecurePath generates a QR code. | A QR code is generated by SecurePath. |
| Click **Save** to confirm. | **Save** should be clicked to confirm. |

### Imperative mood in procedures
Begin every procedure step with an action verb. Do not include the subject "you".

| Correct | Incorrect |
|---|---|
| Click **Settings**. | You should click **Settings**. |
| Enter your current password. | The user enters their current password. |

## 3. Document structure

All SecurePath documentation follows one of three information types. Every document covers exactly one type.

### Concept documents — "What is this?"

Use when: explaining what something is, how it works conceptually, or why it exists.

Required sections:
1. **Summary** — one sentence stating what this topic explains
2. **Overview** — explanation of the subject at a conceptual level (not instructions)
3. **Example** — a concrete, realistic illustration

### Task documents — "How do I do this?"

Use when: providing step-by-step instructions.

Required sections:
1. **Summary** — one sentence stating what the procedure achieves
2. **Prerequisites** — what the reader must have or have completed before starting
3. **Steps** — numbered, one action each, imperative mood
4. **Result** — what the reader sees or has when all steps are complete

### Reference documents — "What are the values or options?"

Use when: providing lookup data such as error codes, field definitions, or configuration options.

Required sections:
1. **Summary** — one sentence describing what the reference covers
2. **Content** — table or list with all values and their descriptions

## 4. Procedures

### One action per step
Each numbered step describes exactly one action. If a step contains two actions connected by "and" or "then", split it.

| Correct | Incorrect |
|---|---|
| 1. Click **Settings**. | 1. Click **Settings** and select **Security**. |
| 2. Select **Security**. | |

### Results
When a step produces a visible system response, add a **Result** line immediately after the step — indented or on a new line, not inside the step itself.

Example:
> 3. Click **Enable passkey**.
> Result: The passkey enrollment dialog opens.

### Prerequisites
List everything the reader needs before the first step. Use a bullet list. Be specific.

---

## 5. Headings

- **Sentence case** throughout: capitalise only the first word and proper nouns
- **Task titles**: How to [verb] [object] — example: "How to set up a passkey"
- **Concept titles**: What is [subject] — example: "What is a passkey"
- **Reference titles**: [Subject] reference — example: "Error codes reference"
- Avoid gerunds in topic titles: "Set up a passkey" — not "Setting up a passkey"
- Do not end headings with a full stop

## 6. Formatting

### UI elements
**Bold** the names of UI elements when instructing the reader to interact with them:
- Click **Save**
- Select **Security**
- Open the **Settings** menu

### Code and technical strings
Use `inline code` for:
- File names: `config.json`
- API endpoints: `/api/v1/passkeys/register`
- Error codes: `PASSKEY_NOT_FOUND`
- Command-line input: `git commit -m "message"`
- System-generated values the reader must copy or enter exactly

### Lists
- Use numbered lists for sequential procedures
- Use bullet lists for non-sequential items only
- Do not mix numbered and bullet items in the same list

### Images
Insert image placeholders wherever a procedure step involves a UI interaction. Use this format:

```
<!-- IMAGE: [description of what the screenshot should show] -->
```

Replace the placeholder with the actual screenshot before publishing.

---

## 7. Writing style

- **Short sentences** — prefer one idea per sentence
- **Plain language** — write for a reader who is competent but not an expert in the subject matter
- **No jargon without explanation** — any technical term introduced for the first time must be briefly explained or linked to a concept document
- **No filler phrases** — avoid "Please note that", "It is important to", "In order to"
- **Consistent tense** — use present tense throughout: "SecurePath displays a QR code", not "SecurePath will display a QR code"
